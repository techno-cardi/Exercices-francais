# Offline SQL import contract

Run `node resultats/tests/sql-setup.mjs` once, then `node resultats/tests/sql-imports.test.mjs`. The setup downloads pinned `@electric-sql/pglite@0.5.12`, checks its SHA-512 integrity and extracts a git-ignored test runtime. Tests create an in-memory PostgreSQL WASM instance from `sql-bootstrap.sql`, then apply the actual migration. No live credentials, student records or remote database connections are involved. PGlite is single-session: these tests verify transactional rollback and stale snapshots but do not reproduce two concurrent database connections.

The migration is prepared for review; it has not been applied remotely. No historical shared assignment is split and no historical grade or note is rewritten. New canonical bases remain null on legacy results. NOT VALID constraints avoid scanning/rejecting old records during migration while checking subsequent writes.

All RPCs are security definer with empty search_path and explicit public-qualified relations. PUBLIC, anon and authenticated execute are revoked; service_role gets only the three API RPCs below. The operations table has RLS enabled, no public policies or grants, and service-role access. Teacher sessions must still be checked by the API before calling; mutation RPCs also require an active teacher and bind operation identity to its stored teacher_email.

- `cardinal_assignment_snapshot(p_assignment_id uuid)`: `{assignment,results}`, using complete snake-case database rows and results sorted by student_email. Assignment includes revision. A single SQL statement produces the consistent snapshot. Missing assignment returns null.
- `cardinal_create_assignment_batch(p_teacher text,p_operation_id uuid,p_assignment jsonb,p_groups text[])`: `{id,assignments:[{id,groupCode}],operationId}`. Groups are deduplicated/sorted and checked against active roster groups. Each gets a distinct assignment. Payload identity ignores id, updated_at and group_codes, which are removed; changed payload for the same operation rejects. Formative linkage fields are rejected in batch copies (scale mode is allowed). Confirmed retry returns the stored result. No Mozaik links are copied.
- `cardinal_confirm_assignment_operation(p_teacher text,p_preview_id uuid)`: consumes a stored unexpired preview and atomically commits it. Expected operation kinds are formative_import, settings_import and mozaik_metadata. Stored confirmed retries return the cached result.

The operation plan has `assignmentId` (UUID or null), `beforeSnapshot` (exact snapshot above or null for new), `assignmentPatch` (DB snake-case fields), `newAssignment` (DB snake-case fields for new), `groupCode`, `writes`, optional `sourceLink` (DB snake-case Formative fields), optional `mozaikLink` ({activity_id,competence_code,group_code?}), and `summary` (counts). Summary is merged into the result and authoritative assignmentId/importedCount/maxScore/operationId take precedence.

Patch/newAssignment fields must omit id, group_codes and updated_at. Allowed fields: title, competencies, weight, max_score, published, instructions, subject, term, activity_date, activity_type, report_card_enabled, mozaik_results_visible, mozaik_show_in_schedule, mozaik_homework, mozaik_period, mozaik_competence_code, mozaik_competence_kind, formative_scale_mode, import_state, source_metadata, formative_id, formative_assignment_id, formative_section_id, formative_title, formative_question_ids, formative_question_meta, formative_last_synced_at. Unknown keys reject. Existing fields absent from the patch remain unchanged. New ready assignments require an explicit max_score; metadata_only can carry null max_score.

Each write has `{email,grade,baseScore,baseMax,sourceKind,response,feedback,visible}`. Non-null grades require canonical bases/source; null bases store a null base_source. Callers supply the complete desired result, including preserved response/feedback/visibility. Email duplicates reject. New result rows require an active student in the exact group. Existing result rows retain assignment membership after a roster move or deactivation and can be rescaled from canonical bases; the API separately rejects new source imports for students outside the current group. An existing assignment can be updated even when its group has no currently active roster entries. Existing destination assignments must have exactly that single group. Confirm locks the operation, assignment and result rows, compares the complete preview snapshot, locks eligible roster rows, then applies the patch/results/link changes. Invalid later writes roll back earlier changes. Mozaik links are dirtied only for the exact assignment/group. Remaining non-null grades must fit the final maximum.

Every assignment UPDATE bumps revision and updated_at. Every result INSERT/UPDATE/DELETE updates/locks its parent, so legacy writes serialize with confirmation and make outstanding previews stale. Concurrent opposite lock ordering can cause PostgreSQL to abort one transaction as a deadlock victim; no partial confirmation commits. APIs should ask for a new preview/retry on this transient database failure. Result identity changes are rejected. New RPCs carry canonical bases; existing legacy result mutation paths must update/re-establish canonical bases if they change a grade.

Errors are database exception tokens, including operation_not_found, operation_teacher_mismatch, operation_payload_conflict, invalid_teacher, invalid_groups, preview_expired, invalid_operation_kind, stale_preview, assignment_requires_single_group, invalid_result_student, duplicate_result_student, unknown_assignment_field, invalid_result_grade, invalid_remaining_result_grade and missing_canonical_base. The API should map these to safe French user messages and appropriate HTTP statuses.
